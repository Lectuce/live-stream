# live-stream 秋招项目技术复盘与性能口径

> 本文用于秋招简历、项目介绍和面试复盘。所有性能数字都来自当前项目的实际测试，严格区分 HTTP QPS、WebSocket 消息输入速率、广播投递率和并发连接数。

## 1. 项目一句话概述

`live-stream` 是一个基于 Go 的直播房间和实时弹幕后端，使用 Gin 提供 HTTP API，使用 WebSocket 维持长连接，通过 Kafka、MySQL 和 Redis 完成弹幕的异步持久化与实时广播，并使用自研工具完成端到端压测和容量边界分析。

## 2. 项目目标

这个项目不只是完成房间 CRUD，而是尝试回答以下问题：

- 用户如何安全注册、登录并维持 Session；
- 房主权限如何落到创建、修改、开播和关播接口；
- 弹幕如何从 WebSocket 进入后端，可靠地持久化并再广播给观众；
- 集中建连、慢客户端、队列积压和并发关闭等问题如何处理；
- 如何用可重复的压测数据证明系统能力，而不是只声称“高并发”。

该项目目前没有真实商业用户和业务收益，因此简历和面试中应突出工程价值、可验证性和问题复盘，不虚构 DAU、收入或成本收益。

## 4. 九项核心能力及实现过程

### 4.1 Gin HTTP API、注册登录和 Redis Session

注册和登录是公开接口，`/auth/me` 和 `/auth/logout` 才需要登录。这避免了“用户还没有账号就被 Auth 拦截”的路由错误。

安全链路包括：

- DTO 使用 `binding` 标签校验用户名、邮箱和密码长度；
- 密码使用 Argon2id 哈希，不保存明文；
- Session ID 使用 `crypto/rand` 生成；
- Session 保存在 Redis，TTL 为 7 天；
- Auth 中间件失败时使用 `AbortWithStatusJSON`，不再继续执行后续 Handler；
- 登录成功后使用 Cookie 传递 `sid`。

这一部分的面试重点不是“会写登录接口”，而是能够解释为什么密码选 Argon2id、为什么 Session 放 Redis、TTL 的意义以及 Cookie 的安全边界。

### 4.2 房间权限、开播/关播和历史消息分页

房间接口分为公开读和鉴权写：

- 房间列表、房间详情和历史弹幕可公开读取；
- 创建、修改、开播和关播必须通过 Auth；
- 创建房间时的 `owner_id` 来自 Session，不信任客户端传入；
- 修改、开播和关播校验当前用户是否为房主；
- 未开播房间的 `start_at` 使用 `NULL`，而不是 MySQL 严格模式不接受的零时间；
- 历史弹幕按房间和游标查询，返回 `has_more`；
- 历史接口单次最多返回 100 条，因此压测中 `History matches: 100` 不表示只持久化了 100 条。

### 4.3 WebSocket 长连接和房间广播

WebSocket 握手时校验：

- `room_id` 格式正确；
- 房间存在且处于开播状态；
- `Origin` 必须在 `allowed_origins` 白名单中；
- 游客可建立连接并接收弹幕，但不能发送弹幕；
- 携带有效 Session 的用户才能发送。

Hub 按 `room_id` 管理客户端集合。每个 Client 包含独立写队列，读和写由独立 goroutine 处理，避免多个 goroutine 直接并发写同一 WebSocket 连接。

### 4.4 Kafka → MySQL → Redis Pub/Sub → WebSocket 完整链路

弹幕的端到端路径为：

1. 登录用户通过 WebSocket 发送弹幕；
2. 服务端填入 `message_id`、`room_id`、`user_id` 和用户名；
3. Producer 把消息写入 `danmu_topic`；
4. Consumer Group 拉取消息；
5. 弹幕先批量写入 MySQL；
6. 落库成功后发布到 Redis Pub/Sub；
7. Redis Subscriber 将消息放入 WebSocket Hub 的广播队列；
8. Hub 将弹幕投递到对应房间的所有在线连接。

这个顺序的语义是：只有 MySQL 落库成功的弹幕才进入实时广播，避免“用户看到了弹幕，但历史记录中没有”的明显不一致。

### 4.5 Kafka Consumer Group、手动提交 offset 和批量落库

Consumer 使用固定 Group ID `live-danmu-consumer`，不使用自动提交，而是在业务处理后调用 `CommitMessages`。

当前策略：

- 最多累积 100 条就处理一次；
- 不满 100 条时，最多等待约 200ms；
- MySQL 批量写入失败时重试；
- 落库最终失败时不发布 Redis，也不提交 offset；
- 批次包含多个 Kafka 分区时，向 `CommitMessages` 传入所有消息，由 kafka-go 分别提交每个分区的最高 offset；
- `message_id` 在 MySQL 中具有唯一索引，为重复消费提供幂等基础。

Producer 已从 `kafka.LeastBytes{}` 改为 `kafka.Hash{}`。相同 `room_id` 作为 Key 后会进入相同分区，从而获得 Kafka 分区层面的房间内顺序。最新的 room 12 和 room 14 服务端日志中，同一房间的批次持续提交到同一分区，符合 Hash 路由预期；后续还应增加多房间自动化断言，避免只靠人工查看日志。

### 4.6 慢客户端队列和背压意识

每个 WebSocket Client 有一个容量为 256 的写队列。Hub 使用非阻塞 `trySend`，不允许一个慢客户端直接卡住整个房间的广播遍历。

这一策略体现了背压意识，但尚未完成生产化：

- WebSocket 写入没有明确 write deadline；
- 队列满时发起注销，但应立即关闭 Socket 以解除阻塞写；
- `trySend=false` 同时可能表示“channel 已关闭”或“channel 已满”，当前日志会把两者都写成 `channel full`；
- 高并发下逐客户端打印日志会反过来放大过载；
- 直接把队列从 256 扩大到数千只会增加内存占用并推迟故障，不是根治方案。

这是项目中很适合面试的取舍：当慢客户端出现时，是保证每条弹幕必达，还是保护整个房间的实时性和可用性。

### 4.7 自动化压测脚本

PowerShell 脚本把以下流程串成一次可重复测试：

```text
go test / go vet
→ HTTP 健康检查
→ 注册测试用户
→ 登录并提取 sid
→ 校验 Session
→ 创建房间并开播
→ 运行 WebSocket benchmark
→ 查询历史弹幕
→ 关播和清理
```

Benchmark 支持：

- 指定总连接数；
- 精确指定发送者数量；
- 只让发送者携带 Session，其余连接按游客监听；
- 控制建连 ramp、warm-up、发送时长和 drain；
- 记录 Dial 尝试、成功、失败和峰值连接数；
- 统计发送弹幕、实际收到的弹幕广播和理论应收数量。

当前脚本还有一个已发现的校验漏洞：只要 `errors=0` 且 `received>0` 就可能打印 PASSED，尚未强制 `received == expected`。最新的 5、6、7、10 个发送者测试分别仍有 0.10%、0.24%、1.14%、8.95% 的最终投递缺口，但都打印了 PASSED。这是下一步必须修复的测试基础设施问题。

### 4.8 10,000 WebSocket 连接测试

当前已证明单机后端可以完成 10,000 个 WebSocket 连接的全量建连：

```text
dial_attempted=10000
dial_succeeded=10000
dial_failed=0
peak_conns=10000
```

这个结果证明了连接容量，但不能单独证明 10,000 连接下的任意广播速率都能无损支持。“连得上”和“每秒能向这些连接发多少消息”是两个不同指标。

### 4.9 真实问题的发现与修复

项目价值不只是最终代码，还包括通过运行和压测暴露问题、建立证据链并修复的过程。

#### 在线人数广播风暴

旧实现每注册或注销一个连接，立即向整个房间广播一次在线人数。集中建立 N 个连接时，客户端投递数接近：

```text
1 + 2 + ... + N = N(N+1)/2
```

修复后，注册和注销只把房间标记为 dirty，独立 worker 每 250ms 最多广播一次最新人数，中间状态直接覆盖。这个修复将“必须尽量送达的弹幕事件”与“只需要最新值的在线状态”分成了不同队列语义。

#### channel 并发关闭

压测曾触发：

```text
panic: send on closed channel
```

根因是广播向 Client 发送的同时，另一个 goroutine 关闭了发送 channel。修复包括：

- `sendMu` 和 `sendClosed` 统一保护发送与关闭；
- `trySend` 负责安全的非阻塞投递；
- `closeSend` 保证 channel 只关闭一次；
- `unregisterOnce` 和 `closeOnce` 保证注销和 Socket 关闭幂等；
- 增加 Hub 并发广播与注销回归测试。

#### 历史数据库表结构

旧数据库中 `users.user_id` 和 `rooms.room_id` 缺少正确的主键和自增属性，导致注册或创建房间返回 ID 0。`go test ./...` 只能证明编译通过，无法检测这类旧库 schema 问题。

在确认仅有测试数据后，清理旧表并由当前 GORM 模型重建，生成正确的 `PRIMARY KEY` 和 `AUTO_INCREMENT`。这一过程说明了单元测试、数据库迁移和运行时验证之间的边界。

#### Kafka 批处理和 offset

先后修复了：

- 成功时继续重试、失败时反而提交 offset 的反向逻辑；
- 阻塞 `FetchMessage` 导致 200ms ticker 无法刷新尾部批次；
- 只有点赞消息时不触发定时处理的条件错误；
- 只提交批次最后一条消息所在分区，忽略其他分区 offset 的问题；
- Producer 初始化只创建对象就打印成功，却未真实连接 Kafka 的假健康问题。

#### Docker 网段和局域网冲突

服务器一度存在：

```text
Docker bridge: 172.19.0.0/16
Windows client: 172.19.97.166
```

Linux 把发往 Windows 的回包错误路由到 Docker bridge，造成 Windows 无法访问 SSH 和 9000 端口。将 Compose 默认网络改为 `10.250.0.0/24` 后，回包恢复从 `enp7s0` 和局域网网关返回。

这个问题展示了压测不仅会暴露代码问题，也会暴露容器网络和主机路由问题。

## 5. 实测数据与严格结论

### 5.1 已完成的端到端测试

| 场景 | 输入 | 理论投递 | 实际投递 | 错误/缺口 | 结论 |
|---|---:|---:|---:|---:|---|
| 100 连接、1 发送者 | 30 条 | 3,000 | 3,000 | 0 | 无损通过 |
| 1,000 连接、10 发送者 | 588 条 | 588,000 | 588,000 | 0 | 无损通过 |
| 10,000 连接、5 发送者 | 293 条 | 2,930,000 | 2,927,140 | 缺 2,860，0.10% | 接近无损，但严格判定未通过 |
| 10,000 连接、6 发送者 | 358 条 | 3,580,000 | 3,571,271 | 缺 8,729，0.24% | 已开始积压，严格判定未通过 |
| 10,000 连接、7 发送者 | 414 条 | 4,140,000 | 4,092,931 | 缺 47,069，1.14% | 退化明显，严格判定未通过 |
| 10,000 连接、10 发送者 | 593 条 | 5,930,000 | 5,399,236 | 缺 530,764，8.95% | 明显过载，脚本误报 PASSED |

Kafka 独立写入验证中，10 条消息全部 delivered，Consumer Group 三个分区最终全部 `LAG=0`。由于样本只有 10 条、持续时间约 10ms，该数据只能证明链路正常，不能用于声称 Kafka 的稳定极限 QPS。

以上 10,000 连接阶梯测试的目标扇出大约是 50,000、60,000、70,000 和 100,000 次投递/秒。它们不是 HTTP QPS，也不是 Kafka 输入 QPS，而是“输入弹幕数 × 房间在线连接数”形成的 WebSocket 投递量。

10 个发送者测试的 drain 阶段中，`lag` 从 1,335,398 持续下降到 530,773，说明相当一部分缺口是尚未排空的队列积压，而不能全部直接解释为服务端永久丢弃。不过在测试结束前仍未送达，就不满足当前测试的实时性和完整性目标，因此仍应判为未通过。若把 drain 无限延长后才补齐，也只能证明最终吞吐，不能证明实时广播能力。

### 5.2 服务端日志的正确解释

10 个发送者测试在客户端输出 `FINAL` 后约 1 秒，服务端集中出现了 29 条 `client send channel full` 和 630 条 `write error`。这些日志与 10,000 个客户端同时关闭的时间重合，其中大量错误是 `broken pipe` 或 `use of closed network connection`，主要属于压测结束时的连接拆除噪声，不能单独作为压测运行阶段掉线的证据。

但这也暴露了两个可观测性问题：

- `trySend=false` 无法区分“发送队列已满”和“连接已经关闭”，日志可能误报为 `channel full`；
- 正常关闭阶段的写错误没有被过滤或限频，10,000 连接同时退出时会形成日志风暴。

同一批日志中 Kafka 批量提交持续成功，同一房间落在同一分区；仅观察到一次约 295ms 的慢 SQL。结合最终 `errors=0`、全程保持 10,000 连接以及 drain 期间仍在追赶，更像是 WebSocket 扇出、网络或压测机接收侧形成积压，而不是 Kafka 链路首先失败。要最终定位责任边界，还需要同时采集服务端队列深度、丢弃计数、网卡吞吐、CPU，以及压测机 CPU 和网卡吞吐。

### 5.3 当前可以声称的能力

可以严谨表述为：

```text
- 单机完成 10,000 个 WebSocket 连接全量建连，Dial 失败数为 0。
- 1,000 连接、约 10 条弹幕输入/秒时，完成约 9,800 次 WebSocket 投递/秒且无损。
- 10,000 连接、目标约 50,000 次投递/秒时，drain 后仍有约 0.10% 投递缺口，接近但没有达到严格无损。
- 目标提高到约 60,000、70,000、100,000 次投递/秒时，最终缺口依次扩大到约 0.24%、1.14%、8.95%。
- 当前严格无损边界只被证明到约 9,800 次投递/秒；10,000 到 50,000 次投递/秒之间尚未完成阶梯定位。
```

不应表述为：

```text
- “支持 10 万 QPS”；
- “10,000 用户可以每人每秒发送一条并全量送达”；
- “生产级零丢失弹幕系统”。
```

## 6. “别人的项目都是好几万 QPS”应该如何理解

### 6.1 先统一指标

QPS 只有在说清“查询什么”之后才有意义。

| 指标 | 当前项目中的含义 |
|---|---|
| HTTP RPS | 每秒处理的注册、登录、房间列表等 HTTP 请求 |
| WebSocket 输入速率 | 客户端每秒发给后端的弹幕条数 |
| Kafka QPS | Producer/Consumer 每秒处理的 Kafka 消息数 |
| DB QPS | MySQL 每秒 SQL 查询或写入次数 |
| 广播投递率 | 每秒向所有 WebSocket 客户端投递的消息总次数 |
| 并发连接 | 同时保持的 WebSocket 数量，它不是 QPS |

弹幕房间存在放大关系：

```text
广播投递率 = 房间弹幕输入条数/秒 × 房间在线连接数
```

例如 10 个发送者每人每秒发 1 条，房间有 10,000 个连接：

```text
输入只有约 10 条/秒
但广播目标是约 100,000 次投递/秒
```

因此不能把这个结果与一个“返回固定 JSON”或“读一次 Redis 缓存”的 HTTP 接口 QPS 直接比较。

### 6.2 为什么很多项目声称几万 QPS

常见原因包括：

- 测试的是无状态、返回小包的 HTTP `GET` 接口；
- 数据全部命中内存或 Redis，不包含数据库写入；
- 没有 Session 鉴权、异步消息、持久化和广播扇出；
- 压测机和服务器在同机或同宿主机，网络成本极低；
- 只报告瞬时峰值，不报告持续时间、延迟分位数、错误率和硬件配置；
- 把压测工具发出的请求数当成服务端完成的请求数；
- 把并发连接数、QPS、TPS 和广播投递数混为一个指标。

这不意味着所有“几万 QPS”都是虚假的，而是必须要求同样的请求语义、硬件、数据一致性、错误率和测试时长才能比较。

### 6.3 当前项目并不是“只有一点 QPS”

当前 1,000 连接成功测试中，弹幕输入只有约 9.8 条/秒，但后端无损完成了约 9,800 次 WebSocket 投递/秒。这是一对多广播工作量，不是只执行了 9.8 次操作。

同时，HTTP API 的最大 RPS 尚未被单独压测，因此既不能说 HTTP 只有 10 QPS，也不能声称它有几万 QPS。正确做法是分别测试：

- 公开房间列表的 HTTP RPS 和延迟；
- 带 Redis Session 的鉴权接口 RPS；
- 带 MySQL 写入的创建/修改接口 TPS；
- WebSocket 建连速率和并发连接数；
- 弹幕输入速率和广播投递率；
- Kafka 和 MySQL 的独立吞吐与积压。

## 7. 秋招简历建议表述

### 7.1 可使用的项目介绍

> 基于 Go、Gin、WebSocket、Kafka、Redis 和 MySQL 实现直播房间与实时弹幕后端，覆盖 Session 鉴权、房主权限、弹幕异步持久化、Redis Pub/Sub 和房间级 WebSocket 广播。

> 针对集中建连时在线人数通知产生的近似 O(N²) 扇出，将其改为 250ms 最新状态合并广播；通过锁、幂等关闭和并发回归测试修复 `send on closed channel`。

> 编写端到端自动压测工具，单机完成 10,000 WebSocket 连接全量建连；在 1,000 连接、约 9,800 次广播投递/秒的场景中实现零错误和零缺口，并通过阶梯压测定位慢客户端队列与单机扇出瓶颈。

### 7.2 不建议的表述

```text
支持 10 万 QPS。
生产级百万弹幕系统。
10,000 用户实时发送且绝不丢失。
使用 Kafka 保证了绝对一致性。
```

这些说法都超出了当前证据边界，面试官只要追问指标口径、延迟、错误率和硬件环境就会暴露。

## 8. 面试时最值得讲的问题

1. 为什么相同 `room_id` 要进入相同 Kafka 分区？
2. 为什么设置了 Kafka Key 后，还必须选择 Hash Balancer？
3. Kafka 只保证分区内有序，如何继续保证房间广播不被多 worker 重新打乱？
4. 为什么 10 条弹幕/秒在 10,000 人房间中会变成约 100,000 次投递/秒？
5. 为什么在线人数通知会在集中建连时形成近似 O(N²)？
6. 为什么扩大每个 Client 的发送队列不能根治慢客户端？
7. Kafka `LAG=0` 为什么不代表 WebSocket 客户端已经无损收到？
8. 为什么 `go test ./...` 无法发现旧 MySQL 表主键错误？
9. 如何区分连接容量、建连速率、消息输入速率和广播投递率？
10. 如何判断一次压测是真通过，而不是压测脚本误报？

## 9. 下一阶段改造优先级

### P0：必须完成

1. 压测脚本强制 `received == expected`，或显式配置可接受丢失率和最大 drain 后积压。
2. 区分 Client channel 已关闭和队列已满。
3. 队列满时立即关闭慢客户端 Socket，并增加 WebSocket write deadline。
4. 过滤正常关闭错误，对慢客户端日志限频，并增加 drop counter，避免退出阶段日志风暴。
5. 测试 10,000 连接下 10,000、20,000、30,000、40,000 次投递/秒，确定严格无损稳定边界。
6. 对多个 `room_id` 增加 Kafka 分区自动化断言，回归验证 Hash 路由和房间内顺序。

### P1：提升项目竞争力

1. 增加 Prometheus 指标：在线连接、输入消息、广播投递、丢弃、队列深度、Kafka 处理失败。
2. 对同一房间广播使用固定分片 worker，在保持并行能力的同时避免房间内乱序。
3. 使用 PreparedMessage 或协议级批量帧，减少重复帧编码和写调用。
4. 增加注册、登录、房间权限、游标分页和 Kafka Consumer 集成测试。
5. 使用 `http.Server.Shutdown` 完成 HTTP 优雅退出，并用 systemd 管理服务进程。
6. 将密码和服务地址改为环境变量，使用 Gin release 模式并配置可信代理。
7. 单独测试 HTTP API RPS、延迟分位数和错误率，不再用 WebSocket 数据代替 HTTP QPS。

## 10. 复盘结论

这个项目当前最有价值的不是使用了多少中间件，而是已经形成了一条可复盘的工程闭环：

```text
实现功能
→ 编写自动测试
→ 在真实运行环境施加负载
→ 通过日志、offset、Lag 和投递缺口建立证据
→ 定位代码、数据库、Docker 网络和客户端队列问题
→ 修复后重新压测
→ 明确已验证能力和未达到的边界
```

对秋招项目而言，这种能够讲清“为什么出问题、如何用数据定位、修复后改善了什么、还有哪些边界”的能力，比没有指标口径的“几万 QPS”更经得起面试追问。
